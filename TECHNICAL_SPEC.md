# D&D IPL — техническое задание первой версии

Статус: принято для реализации; выполнены прототип и серверная основа (версия 0.2). Дата: 17 сентября 2026 года.

Документ определяет состав первой версии D&D Interactive Player List, её архитектуру, интерфейсы и условия приёмки. Исходное описание — D&D IPL.docx; решения из обсуждения с заказчиком имеют приоритет. Реализованы интерфейс и серверная основа: аккаунты, кампании, права доступа, SQLite и синхронизация изменений. Полный игровой контент и удалённое подключение через Tailscale ещё не завершены.

## 1. Назначение и согласованные решения

Приложение помогает мастеру вести персонажей кампании D&D, а игрокам — просматривать актуальные листы и писать заметки. Целевая группа: один мастер и пять игроков, подключающихся из разных домов.

- Правила D&D 2024; исходный набор контента — SRD 5.2.1 с пользовательскими дополнениями.
- Сервер, база, изображения и резервные копии хранятся на ноутбуке мастера.
- Мастер и игроки работают в браузере. Для удалённого подключения выбран Tailscale Personal.
- Обязательные платные сервисы, домен и аренда сервера не требуются. Действующие ограничения стороннего бесплатного тарифа проверяются при настройке.
- Игрок создаёт черновик персонажа и отправляет его на утверждение. После утверждения игровые данные меняет только мастер; игрок может редактировать личные заметки.
- Есть общие сведения, личные заметки игрока, скрытые заметки мастера и скрытые свойства предметов.
- Игровые изменения мастера записываются в историю. Предусмотрены отмена изменений и резервное копирование.

## 2. Границы первой версии

Первая версия включает локальные аккаунты, кампании, приглашения участников, создание и утверждение персонажей, лист персонажа, панель группы, библиотеки предметов, заклинаний и особенностей, инвентарь, базовые расчёты, заметки, историю, резервирование и обновление подключённых браузеров.

Начальный автоматизированный сценарий: персонаж первого уровня без мультикласса, созданный из проверенного поднабора SRD 5.2.1. До реализации набора оформляется перечень поддерживаемых видов, классов, происхождений и особенностей с точными источниками. Этот объём первой поставки согласован; полная автоматизация SRD не входит в него. Расширение библиотеки входит в дальнейший план.

Мастер может вручную вести персонажа более высокого уровня и добавлять текстовые способности. Интерфейс явно различает автоматически рассчитанное значение, ручную поправку и правило, требующее решения мастера.

За рамками первой версии: карта и перемещение жетонов, голосовой чат, броски костей, трекер инициативы, магазин и платежи, генерация через ИИ, импорт закрытых книг, автоматизация всех исключений правил, мультикласс, полноценный мастер повышения уровня, редактирование без связи с сервером, круглосуточный облачный сервер.

## 3. Роли и доступ

Аккаунты принадлежат локальной установке приложения. Роль определяется участием в конкретной кампании. Управляющий установкой мастер создаёт кампании; открытой регистрации нет. Первый аккаунт создаётся при первичной настройке только с самого ноутбука, без стандартного пароля.

| Действие | Мастер кампании | Игрок кампании |
| --- | --- | --- |
| Менять описание и оформление кампании | Да | Нет |
| Приглашать и отключать участников | Да | Нет |
| Видеть листы персонажей | Все в кампании | Только свои |
| Редактировать черновик персонажа | Да | Только свой в состоянии черновика |
| Отправлять персонажа на утверждение | Да | Только своего |
| Утверждать или возвращать персонажа | Да | Нет |
| Менять утверждённый лист и инвентарь | Да | Нет |
| Управлять библиотеками и выдавать карточки | Да | Нет |
| Читать общие заметки | Да | Да |
| Менять общие заметки | Да | Нет |
| Читать и менять личные заметки игрока | Нет через интерфейс и API | Только собственные |
| Читать и менять скрытые заметки мастера | Да | Нет |
| Видеть полную историю и отменять изменения | Да | Нет |
| Создавать и восстанавливать резервные копии | Управляющий установкой | Нет |

Личные заметки защищены правами приложения, но не от владельца ноутбука, который имеет доступ к файлам базы и резервным копиям. Сквозное шифрование личных заметок в первую версию не входит.

Игрок получает доступ только к кампаниям, куда приглашён. Одновременно допускаются несколько персонажей одного игрока; первоначально интерфейс ориентирован на одного активного персонажа на кампанию. Это рабочее проектное решение.

## 4. Основные сценарии

### Подключение

Мастер запускает приложение и Tailscale, копирует адрес приложения и создаёт одноразовое приглашение с ограниченным сроком действия. Игрок подключается к сети Tailscale, открывает ссылку и создаёт локальный аккаунт либо входит в существующий. Приглашение связывает аккаунт с кампанией, но не выдаёт роль мастера. Учётная запись Tailscale и аккаунт D&D IPL независимы.

### Создание персонажа

Состояния: `draft → submitted → approved`. Возврат мастером: `submitted → draft` с комментарием. Утверждённого персонажа игрок самостоятельно в черновик не возвращает.

Анкета: имя, портрет, вид, класс, происхождение, характеристики и допустимые выборы, характер, мировоззрение, цель, мотивация и биография. Для первого этапа предлагается стандартный массив характеристик; значения мастер может поправить. Метод и совместимость выборов проверяет сервер.

Черновик сохраняется автоматически с отображением состояния сохранения. Отправка допускается только после заполнения обязательных полей и проверки выборов. После отправки игрок видит лист и статус рассмотрения, но не редактирует анкету. Мастер утверждает либо возвращает её с пояснением.

### Ведение игры

Мастер открывает обзор группы, выбирает персонажа и изменяет здоровье, ресурс, состояние или другое поле. Сервер проверяет права и версию записи, сохраняет действие, пересчитывает зависимые значения и уведомляет подключённые браузеры. Игрок видит обновление без перезагрузки.

Игрок может рассматривать предметы и способности, но не экипирует, не расходует, не передаёт и не удаляет их самостоятельно. Заявки на действия не входят в первую версию.

### Выдача предмета или способности

Мастер выбирает библиотечную карточку, получателя и количество. Для предмета создаётся экземпляр с собственными состоянием, зарядами, количеством и видимостью свойств. Заклинание или особенность добавляется в соответствующий раздел листа, а не в физический инвентарь.

Изменение шаблона не меняет выданные экземпляры автоматически. Повтор запроса при проблемах связи не создаёт второй предмет. Удаление карточки из библиотеки не уничтожает выданные экземпляры.

### Отключение и восстановление связи

При потере соединения появляется заметный статус. Последний полученный лист остаётся на экране с пометкой о возможной неактуальности; изменения не отправляются в скрытую очередь. Несохранённый текст заметки сохраняется в текущем интерфейсе, а после восстановления пользователь может повторить сохранение. Сохранность такого текста после закрытия вкладки не обещается.

После переподключения клиент запрашивает актуальный снимок доступных данных. При конфликте заметок из двух вкладок приложение предлагает сохранить свою копию или загрузить серверную, не затирая данные молча.

Язык первой версии — русский, с исходными названиями SRD при необходимости. На телефоне лист выстраивается в одну колонку; основные действия мастера не зависят от наведения мыши. Ключевые состояния передаются текстом, а не только цветом. Поиск и пустые списки имеют понятные сообщения; ошибки сохранения не маскируются успешными уведомлениями.

## 6. Модель данных

| Сущность | Основные данные |
| --- | --- |
| User / Session | Логин, хеш пароля, активность; сессия и срок действия |
| Campaign | Название, описание, изображение, набор и версия правил |
| Membership / Invitation | Кампания, пользователь, роль; хеш токена приглашения, срок, использование |
| Character | Кампания, владелец, статус, имя, биография, уровень, исходные значения, версия записи |
| CharacterChoice | Вид, класс, происхождение и выбранные варианты с версиями источников |
| Resource / Condition | Здоровье, временные хиты, ячейки, другие счётчики и состояния |
| ContentDefinition | Тип, название, описание, теги, структурированные поля, версия, источник |
| InventoryItem | Персонаж, снимок шаблона, количество, экипировка, настройка, заряды, раскрытые свойства |
| CharacterAbility | Персонаж, снимок заклинания или особенности, состояние доступности |
| Effect | Источник, цель расчёта, операция, значение, условие активации, состояние |
| Note | Область: личная, общая или мастерская; автор, кампания/персонаж, текст, версия |
| Asset | Локальный путь, тип, размер, принадлежность и видимость изображения |
| ChangeEvent | Автор, время, действие, объект, изменения до/после, идентификатор операции |
| RulePack | Идентификатор, версия, источник и сведения об атрибуции набора правил |

Ключевые сущности хранятся в таблицах со связями и ограничениями. JSON используется для снимков карточек и параметров конкретного типа, а не вместо всей схемы. Все относящиеся к кампании запросы ограничены её идентификатором и членством пользователя. Файлы выдаются с теми же проверками видимости, что и карточки.

Библиотека первой версии относится к кампании; импорт и экспорт пользовательского набора позволят переносить карточки. Персонаж также принадлежит одной кампании; перенос между кампаниями не входит в начальный сценарий.

## 7. Расчёт правил

Модуль правил отделён от интерфейса и базы. На вход получает исходные характеристики, выборы персонажа, экипировку, активные эффекты и ручные поправки; возвращает итоговые значения и объяснение источников.

Первая автоматизация: модификаторы характеристик, бонус мастерства, выбранные владения и экспертиза, навыки и спасброски, базовые формулы защиты выбранного набора, инициатива, вес инвентаря и явно поддержанные числовые эффекты. Остальные особенности могут оставаться текстовыми с пометкой «учитывается мастером».

Правила совмещения бонусов и альтернативные формулы задаются явно и проверяются по SRD. Произвольное выполнение кода из пользовательской карточки запрещено. Ручная поправка хранится отдельно с пояснением; пересчёт не удаляет её.

Изменение максимума здоровья не должно молча лечить или наносить урон: сервер предлагает допустимое изменение текущего значения и включает его в действие мастера. Сложные эффекты требуют явного включения мастером, если их условие нельзя вычислить из поддерживаемых данных.

Каждая автоматизированная механика должна иметь ссылку на источник и тесты на обычный случай, границу и взаимодействие с другими эффектами. Версия набора закреплена за кампанией; обновление контента не меняет существующую игру автоматически.

## 8. Архитектура и хранение

Один сервер Node.js + Fastify обслуживает собранный интерфейс React + TypeScript, HTTP API и WebSocket на одном адресе. SQLite находится на том же ноутбуке; браузеры не обращаются к базе напрямую. Работа без интернета возможна локально, если интерфейс и ресурсы уже установлены; удалённая игра требует доступного соединения.

Предлагаемая структура исходников:

```text
apps/web             интерфейс
apps/server          API, сессии, доступ, хранение и события
packages/rules       вычисления D&D
packages/contracts   схемы запросов и ответов
content/srd-5.2.1     проверенный исходный контент и атрибуция
tests                интеграционные и браузерные сценарии
docs                 решения и инструкции
```

Данные установки: `database.sqlite`, папка изображений и каталог резервных копий. Данные, ключи и пароли исключаются из Git. Изменения схемы выполняются версионированными миграциями с резервной копией перед обновлением.

Сервер — единственный источник истины. Каждая мутация содержит идентификатор операции и ожидаемую версию записи. Сохранение состояния, события истории и сведений о выполненной операции выполняется одной транзакцией. Повтор операции возвращает ранее полученный результат. Уведомление WebSocket отправляется после фиксации транзакции и только допущенным пользователям; после разрыва клиент получает новый снимок.

## 9. Доступ и эксплуатация

- Пароли хранятся как стойкие солёные хеши; применяются ограничение попыток входа и отзыв сессий.
- Сессии передаются в HttpOnly cookies; для запросов, меняющих данные, проверяются происхождение и защита от CSRF. WebSocket также проходит аутентификацию и проверку Origin.
- Предпочтительно настроить HTTPS внутри Tailscale; точный способ проверяется на целевой Windows-установке перед выпуском.
- Политика Tailscale разрешает игрокам доступ только к порту приложения на ноутбуке мастера. Сервер не публикуется в открытом интернете.
- При отключении участника прекращается доступ как через API, так и через уже открытый WebSocket.
- Для портретов первоначально допускаются JPEG, PNG и WebP с проверкой содержимого, ограничением размера и повторным кодированием. Активный HTML/SVG не принимается.
- Пользовательский текст выводится безопасно; секретные свойства не отправляются игроку даже в скрытых полях ответа.
- Журналы диагностики не содержат паролей, токенов и текста личных заметок.
- Первый запуск и восстановление резервной копии доступны только локально на ноутбуке мастера.

Сон, выключение и отсутствие интернета у мастера прекращают удалённую игру. Инструкция запуска включает проверку питания, соединения и адреса. Настройка системы не должна незаметно менять параметры сна пользователя.

## 10. История и резервные копии

Текущая реализация резервирования: ежедневные согласованные снимки SQLite с хранением последних 10 автоматических копий, ручные снимки, локальная проверка и восстановление через `pnpm backup`. Восстановление требует остановленного сервера, создаёт защитный снимок, сбрасывает сессии и приглашения. Поддерживается схема 3; перед обновлением более старой схемы сохраняется отдельная копия. Управление копиями в интерфейсе и включение будущих изображений ещё не реализованы. Инструкция: `docs/BACKUPS.md`.

История записывает игровые действия мастера, утверждение персонажей, выдачу предметов и изменение карточек. Автоматические изменения связываются с исходным действием. Текст личных заметок не попадает в доступную мастеру историю.

Первая отмена поддерживается для последнего изменения игрового состояния конкретного персонажа, если его версия с тех пор не изменилась. Отмена создаёт новое событие и восстанавливает согласованное состояние целиком. Если последующие изменения создают конфликт, операция отклоняется с объяснением. Произвольный откат любого исторического события не обещается.

Резервная копия включает согласованный снимок SQLite, изображения, пользовательские карточки и версии данных. Снимок создаётся средствами резервирования SQLite, а не простым копированием работающего файла. Предлагаемый режим: ежедневно при работающем сервере, вручную и перед обновлениями; последние 10 успешных автоматических копий сохраняются.

Восстановление проверяет формат архива, целостность и совместимость версии, создаёт копию текущего состояния, останавливает запись и затем заменяет данные. Активные сессии сбрасываются. Копии на том же диске не защищают от его поломки: интерфейс предусматривает экспорт на другой носитель без обязательного облачного сервиса.

## 11. План реализации и приёмка

| Этап | Результат | Проверка завершения |
| --- | --- | --- |
| 1. Прототип | Основные экраны на демонстрационных данных | Можно пройти вход, кампанию, анкету, лист и выдачу предмета; проверен телефонный размер |
| 2. Основа сервера | Аккаунты, членство, SQLite, права и кампании | Чужая кампания недоступна прямым запросом; данные переживают перезапуск |
| 3. Персонаж и синхронизация | Черновик, рассмотрение, лист, здоровье, заметки | Два браузера видят изменение; игрок не меняет утверждённые данные |
| 4. Библиотеки | Редакторы, инвентарь, способности, скрытые свойства | Повтор выдачи не дублирует предмет; секретные данные отсутствуют в ответе игроку |
| 5. Правила | Утверждённый перечень SRD и базовые вычисления | Пройдены тесты расчётов и явно обозначены ручные механики |
| 6. Эксплуатация | История, отмена, копии, запуск и Tailscale | Проверены восстановление, переподключение и доступ из другой домашней сети |

Общий сценарий приёмки: мастер создаёт кампанию и приглашает игрока; игрок создаёт персонажа; мастер возвращает его, затем утверждает; выдаёт предмет и меняет здоровье; игрок видит изменения, пишет заметку и не может менять игровые поля. После перезапуска сохранены данные; после восстановления копии получено ожидаемое состояние.

Целевая нагрузка — шесть одновременных участников, с проверкой дополнительных вкладок. Ориентир обновления листа — до одной секунды при устойчивой сети; задержки внешнего соединения измеряются отдельно от времени обработки сервера. Проверяются актуальные браузеры на Windows и реальные телефоны участников; конкретная матрица устройств уточняется перед приёмкой.

Обязательные проверки: обход прав прямым API, изоляция изображений и секретов, отзыв доступа, конфликт двух вкладок, повтор мутации, потеря связи, ошибка сохранения, пересчёт зависимых значений, отмена и восстановление архива.

## Реализованный блок: игровые ресурсы

Персонаж содержит до 50 ресурсов (ячейки круга 1–9 или расходуемые способности). Мастер задаёт максимум, остаток, добавляемые количества короткого/долгого отдыха. Серверная операция resource расходует/возвращает единицу или восстанавливает ресурсы атомарно с проверкой версии; все изменения входят в историю и отмену. Игрок только читает. Отдых пока не автоматизирует здоровье, кости хитов, условия правил и эффекты. Таблицы SQLite не изменены. См. docs/RESOURCES.md.

## Реализованный блок: числовые поправки

В JSON персонажа добавлен список adjustments: до 50 записей с UUID, открытым названием источника, целью, целым ненулевым значением от −30 до +30 и признаком активности. Сервер рассчитывает итоговый КД отдельно от базового ac, прибавляет активные значения к инициативе, навыкам и спасброскам. Пассивная внимательность использует итоговый навык. Изменение доступно мастеру, проверяет версию и записывается в историю; секретного поля в поправках нет. Применимость и сочетание эффектов определяет мастер. Миграция таблиц не требуется.

## Реализованный блок: эффекты экипировки

Item.effects содержит до 26 уникальных целей с целыми ненулевыми поправками −30…+30. Сервер проверяет схему при редактировании библиотеки, импорте и изменении инвентаря. calculateRules добавляет эффекты экипированных предметов с выполненной необходимой настройкой в список источников. Поля предмета и базовые значения не переписываются. Источник не содержит скрытого свойства. Шаблоны и выданные экземпляры независимы; новые поля входят в существующие JSON без миграции.

JSON персонажа дополнен conditions (до 20 записей с UUID, названием, источником, длительностью и пояснением) и concentration (одна запись с названием, длительностью и пояснением либо null). Схема строгая, изменения только мастером с версией и историей. Поля публичны для владельца-игрока. Механическое применение, таймеры и автоматическое снятие не реализованы. ## Реализованный блок: вес инвентаря

Item.weightGrams — необязательное целое число 0…1 000 000 000. Отсутствие поля отличается от нулевого веса. ## Каталог создания персонажа

Схема SQLite 4: character_options(campaign_id, id, data). Встроенные карточки shared/character-options.json объединяются с переопределениями кампании по ID. Новые пользовательские ID — UUID; тип существующей карточки неизменен. До 200 пользовательских записей/переопределений на кампанию. Запись только мастером с оптимистической версией кампании. Сервер проверяет originChoices, доступность и категорию карточек, сам определяет названия и снимки originCards. Неизменный выбор сохраняет прежний снимок. Архив разрешён только для уже выбранной карточки. Старые анкеты без ссылок продолжают поддерживаться. Все описания публичны участникам кампании.


## Выборы первого уровня

OriginCard.boostAbilities — необязательный набор ровно трёх уникальных индексов 0–5, только для background. Character.firstLevel — строгий объект boosts (шесть целых 0–2, сумма 3) и languages (два различных обычных языка). Сервер проверяет прибавки против originCards.background из разрешённого снимка; клиентские снимки не принимаются. Итоги вычисляются из draft.stats и сохраняются рядом с baseStats. Старый starter и firstLevel взаимно исключены, способ создания сохранённой анкеты неизменен. Таблицы/схема базы не меняются, поля входят в существующие резервные копии JSON.


## Владения происхождения

OriginCard.trainedSkills: два уникальных ID из shared/skills.json; toolOptions: 1–20 уникальных строк до 80 символов. Оба поля разрешены только background. FirstLevel.tool выбирается из серверного снимка; фиксированный вариант назначается сервером. Результат backgroundTraining содержит skills/tools/source; клиент не может его записывать. calculateRules использует max(ручная ступень, 1 от активного происхождения). backgroundTrainingEnabled доступен в мастерском patch с версией, историей и отменой. Ручные skillRanks не перезаписываются, миграция таблиц не требуется.


## Классовые владения

OriginCard.classRules (только class) хранит count 1–4, уникальные ID skills и два уникальных saves. Опциональный firstLevel.classSkills включает серверную проверку количества, списка и отсутствия пересечений с навыками происхождения. Отсутствие поля сохраняет ручной режим. Сервер создаёт classTraining по разрешённому снимку карточки, подмена клиентом исключена. Расчёт навыков берёт максимум ступеней, спасброски — объединение владений. Мастерский classTrainingEnabled выключает источник; patch поддерживает версию, историю и отмену. Схема SQLite не меняется.


## Экспертиза

classRules.expertiseCount: 0–2, необязательное (по умолчанию 0). firstLevel.expertise: до двух уникальных ID навыков. При включённом classSkills сервер требует точное число и проверяет принадлежность объединению классовых и фоновых навыков. Проверенный список сохраняется в classTraining.expertise. Расчёт применяет ступень 2 только при активном источнике класса и наличии базового владения. Максимум с ручными ступенями предотвращает повторное начисление. JSON-поля совместимы с существующими копиями базы.


### Классовое снаряжение — реализовано 19.09.2026

В общем создании первого уровня при включённых владениях класса сохраняются базовые владения оружием, доспехами и инструментами всех 12 классов. Дополнительные владения от Divine Order / Primal Order, мультикласс и особенности следующих уровней остаются следующими блоками. Следующий шаг: общие хиты первого уровня и стартовое снаряжение, затем особенности классов и видов.

Источники: [Basic Rules 2024 — классы](https://www.dndbeyond.com/sources/dnd/br-2024/character-classes), [инструменты](https://www.dndbeyond.com/sources/dnd/br-2024/equipment).


### Хиты и стартовое снаряжение — 19.09.2026

В общей анкете firstLevel появился независимый выбор расчёта хитов: кость класса + модификатор итогового Телосложения + настроенные firstLevelHpBonus выбранных карточек. Для дварфа задан +1. Мастер может настроить кость класса и прибавки в редакторе. Способ расчёта фиксируется при первом сохранении; расчёт работает только при сохранении черновика, не лечит утверждённых персонажей и не заменяет ручные правки мастера. Прочие бонусы черт (включая Tough) пока не назначаются автоматически.

Все 12 классов имеют выбор денежной альтернативы или стартового набора; у воина два набора. Бард выбирает один музыкальный инструмент для выдачи, монах — инструмент своего выбранного владения. Происхождение отдельно предлагает 50 зм вместо набора; готовые наборы происхождений остаются следующим шагом. Общая анкета по-прежнему требует настроенных прибавок происхождения (преднастроены пять происхождений; остальные настраивает мастер).

Выдача серверная, со стабильными ID first-level:<character-id>:*. Повторное сохранение заменяет только выданные этим механизмом позиции, сохраняя прочие предметы; отмена выбора убирает стартовую выдачу в черновике. В биографии остаётся начальный расчёт и сумма, текущие деньги находятся в инвентаре. Снимки карточек сохраняют правила старых анкет. Старые персонажи без новых выборов не меняются.

Наборы путешественника/учёного и другие комплекты хранятся одной позицией. Состав готовых классовых наборов пока не редактируется в интерфейсе; после выдачи мастер меняет инвентарь. Автоматической экипировки, веса, урона и КД у этих позиций нет. Следующие блоки: наборы происхождений, детализация предметов, боевые расчёты, особенности и черты.

Проверка: 46 тестов; все классы и наборы, отрицательный модификатор Телосложения, дубли, замена выдачи, фиксация способа расчёта, защита от подмены и права после отправки.

Источники: [классы](https://www.dndbeyond.com/sources/dnd/br-2024/character-classes), [начальные хиты](https://www.dndbeyond.com/sources/dnd/br-2024/creating-a-character), [происхождения и дварф](https://www.dndbeyond.com/sources/dnd/br-2024/character-origins).


### Наборы происхождений — 20.09.2026

Добавлены готовые наборы четырёх происхождений из открытых Basic Rules 2024: послушник, преступник, мудрец, солдат. В анкете независимо выбираются набор/золото/выдача мастером для класса и происхождения. Солдат получает игровой набор из выбранного владения происхождения. У остальных происхождений пока доступно золото или выдача мастером.

Новый firstLevel.backgroundEquipment заменяет переключатель backgroundGold в интерфейсе; старое поле читается для совместимости. Сервер отвергает конфликт «набор + старое золото», неизвестные наборы и неподходящие инструменты. Предметы происхождения имеют отдельные стабильные ID внутри first-level:<id>:background:; замена набора на золото удаляет предыдущую стартовую выдачу, сохраняя сторонние предметы. Сохранённая версия карточки остаётся источником правил. После отправки игрок не меняет выдачу.

Свойства оружия, вес и КД стартовых предметов пока не автоматизированы. Следующий блок — структурированные свойства предметов и разворачивание комплектов. Проверено: 48 тестов, включая состав четырёх наборов, повторное сохранение, смену варианта, старые анкеты, снимки каталога и запрет правок после отправки.

Источник: [Basic Rules 2024: Character Origins](https://www.dndbeyond.com/sources/dnd/br-2024/character-origins).


### Снаряжение и бой — 20.09.2026

Реализован единый боевой профиль предмета: оружие (категория, тип атаки, кости/тип урона, свойства, универсальный урон, дальность, мастерство, магические прибавки) или доспех/щит (категория, база КД, магическая прибавка, Сила, помеха Скрытности). Справочник содержит 35 профилей оружия и 13 доспехов/щита. Профиль и вес можно перенести в шаблон или выданный экземпляр; поля редактирует мастер. Вес переведён из фунтов в граммы с округлением. Конное копьё и огнестрельное оружие пока не преднастроены.

Новые стартовые наборы содержат профили соответствующего оружия/доспехов в снимках карточек. Старые снимки и ранее выданные предметы не переписываются; мастер может назначить им профиль в редакторе инвентаря. Профили не выводятся из названия предмета на сервере.

В листе появились атаки экипированным оружием: модификатор Силы/Ловкости, бонус мастерства один раз при владении, отдельные магические прибавки. Фехтовальное использует больший модификатор; метательное оружие ближнего боя сохраняет Силу/фехтовальное. Владение берётся из активных сохранённых классовых владений (включая исключения монаха/плута) либо из явного решения мастера у предмета. У старого стартового шаблона воина учитываются его владения.

Новый режим acMode=equipment включается только мастером в параметрах персонажа. База: без доспеха 10+Ловкость; лёгкий +Ловкость, средний +Ловкость максимум +2 (отрицательная сохраняется), тяжёлый без Ловкости. Щит учитывается только при владении. Несколько доспехов/щитов вызывают предупреждение и возврат к ручной базе вместо сложения. Существующие числовые эффекты/поправки прибавляются один раз после базы; мастер не должен дублировать записанный бонус профиля в эффектах. По умолчанию старые листы остаются на ручном КД.

Физические свойства предмета действуют и без настройки, магические прибавки профиля — после требуемой настройки. Предупреждения показывают ограничения тяжёлого оружия, две руки при щите, Силу доспеха, отсутствие владения доспехом, Скрытность и боеприпасы. Ограничения не заменяют решения мастера и не блокируют броски/заклинания автоматически.

Это обычные атаки оружием: боевые стили, монашеская замена характеристик/костей, критические попадания, дополнительная атака лёгким оружием, применение мастерства, особая защита монаха/варвара и магии, дистанция до цели, действия, расход боеприпасов и броски пока ручные. Содержимое походных комплектов не разворачивается.

Валидация строгая на сервере; профили доступны существующим библиотеке/выдаче/импорту и истории с отменой, новых таблиц БД не нужно. Проверка: 52 теста, включая матрицу КД/атак, владения, настройку, конфликты, права игрока и отмену.

Источник: [Basic Rules 2024 — Equipment](https://www.dndbeyond.com/sources/dnd/br-2024/equipment). Используется существующее указание авторства SRD 5.2.1 / CC BY 4.0 в листе.
